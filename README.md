# URL Shortener API

A URL shortener built with FastAPI, PostgreSQL, and SQLAlchemy 2.0 (async).

POST a long URL, get a short code back. Hit the short code, get redirected.

| Method | Path                  | What it does                                             |
| ------ | --------------------- | -------------------------------------------------------- |
| POST   | `/shorten`            | Store a long URL, return the shortened one                |
| GET    | `/{short_code}`       | Redirect to the original URL                              |
| GET    | `/stats/{short_code}` | Look up a link and its click count without following it   |
| GET    | `/health`             | Liveness check                                            |

The first two are what the task asked for. I added `/stats` so the click counter is
actually observable (and so the tests can check it without following redirects out to the
real internet), and `/health` because anything that runs behind a load balancer needs
something cheap to poll.

Interactive docs are generated by FastAPI at `/docs` once the server is running.

## Running it

### With Docker

One command, nothing to install but Docker itself:

```bash
docker compose up --build
```

That builds the API image, starts PostgreSQL 16, waits for the database to actually accept
connections, then starts the app on http://localhost:8000. Open
http://localhost:8000/docs to poke at it in a browser.

The wait matters. Postgres takes a few seconds to become ready after its container starts,
so the API depends on the database's healthcheck rather than just its existence. Without
that, the app tries to create its table too early and exits.

Run the tests inside the container:

```bash
docker compose exec api pytest -v
```

Stop everything with `docker compose down`, or `docker compose down -v` to throw away the
stored links too.

### Without Docker

You need Python 3.11+ and PostgreSQL 14+.

**1. Set up the environment**

```bash
python -m venv .venv
source .venv/bin/activate        # Windows PowerShell: .venv\Scripts\Activate.ps1
pip install -r requirements.txt
```

**2. Start PostgreSQL and create the databases**

```bash
sudo service postgresql start    # or however your system starts it
createdb urlshortener
createdb urlshortener_test       # only needed for the tests
```

**3. Configure**

```bash
cp .env.example .env
```

The defaults assume `postgres:postgres@localhost:5432`. If that's not you, point
`DATABASE_URL` at your own instance:

```
DATABASE_URL=postgresql+asyncpg://user:password@localhost:5432/urlshortener
```

The `+asyncpg` part matters. It tells SQLAlchemy to use the async driver, and leaving it
off will fail at startup.

**4. Run**

```bash
uvicorn app.main:app --reload
```

The `short_urls` table gets created on startup, so there's no migration step either way.

If you want the database in Docker but the app on your machine, which is the fastest loop
for actually editing code, start just the database with `docker compose up -d db` and then
run uvicorn as above.

## Trying it out

```bash
curl -X POST http://localhost:8000/shorten \
     -H "Content-Type: application/json" \
     -d '{"url": "https://www.wikipedia.org/wiki/Uniform_Resource_Locator"}'
```

```json
{
  "short_code": "2lSMROY",
  "short_url": "http://localhost:8000/2lSMROY",
  "original_url": "https://www.wikipedia.org/wiki/Uniform_Resource_Locator",
  "visit_count": 0,
  "created_at": "2026-08-21T11:29:18.187883Z",
  "last_visited_at": null
}
```

```bash
curl -i http://localhost:8000/2lSMROY
```

```
HTTP/1.1 307 Temporary Redirect
location: https://www.wikipedia.org/wiki/Uniform_Resource_Locator
```

```bash
curl http://localhost:8000/stats/2lSMROY     # same body, plus the updated visit_count
```

Posting a URL that's already been shortened gives you back the existing code instead of
minting a new one, so retries are safe and the table doesn't fill up with duplicates.

Bad input returns 422 with a `{"detail": "..."}` body. Unknown codes return 404 with the
same shape. Every error response looks the same, so a client only needs one branch to
handle them.

## Layout

```
app/
  config.py      settings, read from .env
  database.py    async engine, session factory, request dependency
  models.py      the short_urls table
  schemas.py     request/response models
  shortcode.py   base62 code generation
  crud.py        database queries
  main.py        routes, startup, error handling
tests/
  conftest.py         test database + HTTP client fixtures
  test_api.py         every endpoint, end to end
  test_shortcode.py   code generation, no DB needed
Dockerfile            image for the API
docker-compose.yml    API + PostgreSQL
```

`main.py` only deals with HTTP: status codes, validation, redirects. `crud.py` only deals
with the database. Splitting them keeps each file short enough to read in one go and means
the query layer can be tested on its own.

## Tests

```bash
pytest -v
```

20 tests, and they run against real PostgreSQL rather than an in-memory SQLite stand-in.
That was on purpose: the three things most worth testing here are the UNIQUE constraint on
`short_code`, the server-side `now()` defaults, and the atomic counter increment, and none
of those behave the same way (or exist at all) on another engine.

They cover code generation, creating and reusing short codes, rejecting malformed URLs,
the redirect status and Location header, click counting, and 404s for both unknown codes
and junk that couldn't be a code in the first place. Each test gets a freshly created and
dropped schema, so nothing leaks between them.

If your test database lives somewhere else:

```bash
TEST_DATABASE_URL=postgresql+asyncpg://user:pass@host:5432/urlshortener_test pytest -v
```

## Decisions worth explaining

**Random codes instead of encoding the row ID.** Base62-encoding the primary key is
cheaper, since you never have to check for collisions. But then `/1`, `/2`, `/3` walks the
entire database and every link anyone has ever shortened is readable by a stranger. Random
7-character codes cost one extra round trip in the rare collision case. 62^7 is about 3.5
trillion, so at any realistic volume collisions basically don't happen.

**The UNIQUE constraint handles collisions, not a pre-check.** The obvious version is
"generate a code, SELECT to see if it's taken, INSERT if it isn't". That's a race: two
workers can both pass the check and one write quietly wins. Instead `create_short_url()`
inserts optimistically and catches `IntegrityError`, retrying with a fresh code up to five
times. Postgres is the only thing that sees all the writes, so it should be the one to
decide. Running out of retries returns 503 rather than 500, since that's a capacity
problem and not a broken request.

**Click counting happens in SQL.** `register_visit()` runs
`UPDATE ... SET visit_count = visit_count + 1` instead of reading the row, adding one in
Python, and writing it back. Under concurrent traffic the read-modify-write version drops
counts.

**307 instead of 301.** Most shorteners return a permanent redirect and browsers cache it
hard, which means later clicks never reach the service again. That freezes the counter and
makes a link impossible to retire or repoint. A temporary redirect keeps the service in
the loop. 307 specifically rather than 302 because it preserves the request method.

**Junk paths get a 404, not a 422.** `/favicon.ico` can't possibly be a code this service
issued, so it's rejected on the alphabet check before the database ever sees it. 404 is
the truthful answer there: the thing doesn't exist.

**`create_all()` on startup instead of Alembic.** For something this size it keeps setup
to one command. A real deployment wants versioned migrations, which is the first item in
the list below.

## Schema

```
     Column      |           Type           | Nullable |  Default
-----------------+--------------------------+----------+-----------
 id              | bigint                   | not null | nextval(...)
 short_code      | character varying(16)    | not null |
 original_url    | character varying(2048)  | not null |
 visit_count     | bigint                   | not null | 0
 created_at      | timestamp with time zone | not null | now()
 last_visited_at | timestamp with time zone |          |

 "short_urls_pkey"           PRIMARY KEY, btree (id)
 "ix_short_urls_short_code"  UNIQUE, btree (short_code)
 "ix_short_urls_original_url" btree (original_url)
```

The unique index on `short_code` does two jobs: it makes the redirect lookup an index scan,
and it's the concurrency guard described above. The index on `original_url` supports the
duplicate check. Timestamps are `timestamptz` so the stored instant means the same thing
regardless of where the server is.

2048 characters for `original_url` is the practical URL length ceiling in browsers, and
the Pydantic schema enforces the same limit so a too-long URL fails validation instead of
blowing up at the database.

## Troubleshooting

**`ConnectionRefusedError: [Errno 111] Connection refused` on startup.** Nothing is
listening on 5432. Check with `pg_isready -h localhost -p 5432`. On WSL, Postgres doesn't
come back automatically after a restart, so you need `sudo service postgresql start`
again.

**`password authentication failed for user "postgres"`.** The credentials in `.env` don't
match your install. Either edit `.env` or set the password to match with
`sudo -u postgres psql -c "ALTER USER postgres PASSWORD 'postgres';"`.

**Edits not picked up by `--reload` on WSL.** File watching doesn't get events across the
`/mnt/c` Windows mount. Move the project inside the Linux filesystem, or restart the server
by hand.

**`port is already allocated` from `docker compose up`.** Something already owns 5432,
usually a PostgreSQL installed directly on the machine. The host-side port isn't used by
the app, so the quickest fix is to move it:

```bash
DB_PORT=5433 docker compose up
```

On Windows with Docker Desktop, note that ports bind on the Windows host rather than
inside WSL, so a PostgreSQL service running on the Windows side will collide even when
nothing in WSL is listening.

## With more time

- Alembic migrations, so schema changes are versioned and reversible.
- Rate limiting on `/shorten`. An open shortener is a great tool for laundering phishing
  links, and that's the first thing to lock down before exposing it.
- Custom aliases and expiry dates. The schema takes two more columns and the generation
  code already reserves the app's own routes so a custom alias can't shadow `/docs`.
- Redis in front of the redirect lookup. Reads outnumber writes enormously and the code
  to URL mapping never changes, so it caches perfectly.
- Move click counting onto a queue so analytics writes stop adding latency to the redirect
  itself.
- A multi-stage Docker build. The current image installs the full requirements file,
  including pytest, so it's larger than a production image should be. I kept it that way
  deliberately so the tests can be run inside the container.

I stopped here because the brief said 1 to 2 hours, and past this point I'd be building a
product rather than showing how I'd approach one.
